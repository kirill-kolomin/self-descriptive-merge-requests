# self-descriptive-merge-requests

An [Agent Plugin](https://agent-plugins.org/) that makes AI-authored merge requests explain themselves.

When an agent writes the code, the reviewer is the only person in the loop who does not know why anything is the way it is. So the review becomes an interrogation: *why this order? what did this change? who calls this? is this related to that other file?* - a round-trip per question, each one a context switch for both sides.

This plugin has the agent answer those questions **in the Changes tab**, where review actually happens: a map of the change, an explanation on every changed file, and short notes on the genuinely non-obvious lines. All are written in plain language. Nothing here adds comments to your source files.

Once installed, ask your agent things like:

- "Annotate this MR for reviewers"
- "Explain this PR so nobody has to ask me why"
- "I pushed new commits - re-check the MR comments"

## Install

**Using the [skills CLI](https://skills.sh):**

```bash
npx skills add kirill-kolomin/self-descriptive-merge-requests
```

**Using GitHub CLI (Copilot, other `gh skill`-compatible clients):**

```bash
gh skill install kirill-kolomin/self-descriptive-merge-requests
```

**Manually, for any client:** clone this repo, then point your client at it the way it documents loading local plugins (most read from a plugins/extensions directory or a config file listing plugin paths).

## What it posts

### 1. One summary in the diff

The reviewer's entry point is anchored to the first changed file in the reading order, not posted as an Overview-only comment. It carries:

- **Intent** - what problem this MR solves and why this approach, in plain language.
- **Behavior: before → after** - what an observer of the running system would notice, including what is *not* changing but looks like it should be.
- **Entry points** - how the changed code is reached from a real entry point (HTTP route, CLI command, event handler, cron, exported API), bounded at three levels.
- **Reading order** - which file to open first, which are mechanical follow-through.
- **An index of the lines explained by inline notes**, linking straight to the code.

### 2. One comment on every changed file

Mandatory coverage: a reviewer opening any file in the diff finds an explanation of it. The only exemption is **autogenerated output** - lockfiles, `dist/`, snapshots, codegen, minified bundles.

These are posted as *file-level* comments (`subject_type=file` on GitHub, `position_type=file` on GitLab), so they attach to the file header instead of interleaving with code lines.

What varies is length, not existence:

```markdown
**Role:** Owns invoice total calculation.

**Why it changed:** Tax was applied after rounding, so multi-item invoices drifted by up to
a cent per item (#4412). The order of the two operations is now fixed.

**Before → after:** Totals on multi-item invoices change by at most 1 cent. The stored
rounding mode is untouched, so historical invoices are unaffected.

**Reached from:** `POST /api/orders` → `OrderController.create` → `PricingService.quote`
```

...while a mechanical file gets exactly one line, written so you can skip it with confidence:

```markdown
Import paths only - follows the rename of `PricingService`; no behavior change.
```

A deleted file gets one line on why it is gone and what replaced it - often the most useful annotation in the whole MR.

**Spec and test files get a different shape entirely** - a list of the cases the file now contains, each with a status:

```markdown
**Covers:** `PricingService.quote`

**Changed cases**

- **applies tax after rounding** - `adapted` (expectation): expected total changed
  12.00 → 12.01, because tax is now applied before rounding. The old number encoded the bug.
- **keeps per-tenant rounding independent** - `added`: two tenants with the same cart
  must not share a rounded total.
- **rejects a negative tax rate** - `removed`: validation moved into `TaxRate.parse`.

**Unchanged (2):** returns 0 for an empty cart; is deterministic
```

The entry-point graph is meaningless for a spec (nothing calls it), and this list answers what a reviewer actually asks: what is covered now, and what did this MR touch. The statuses are **computed** by comparing case bodies between the two revisions - across JS/TS, Python, Go, Rust, JVM, .NET and Gherkin naming - not read off the diff by eye.

`adapted` is the status that earns this whole layer: it is where an AI quietly changes an expectation so a failing test agrees with the code. So an adapted case must say whether the *call shape* changed (signature, mocks, fixtures - routine) or the *expectation* changed (the asserted value - read it carefully), and a removed case must say where its coverage went.

### 3. A few inline comments, only where the code is genuinely non-obvious

This is the one layer with a judgment call. Each comment is anchored to a diff line and scoped to that hunk - three to six lines, readable inside a diff view:

```markdown
**Why:** Tax must be applied before rounding, otherwise each line item rounds twice
and invoices drift by up to a cent per item - the bug in #4412.

**Before → after:** Totals change by at most 1 cent on multi-item invoices; the stored
rounding mode is unchanged, so historical invoices are not affected.

**Reached from:** `POST /api/orders` → `OrderController.create` → `PricingService.quote`
```

### 4. Cross-references between changes in the same MR

When a change supports another significant part of the MR, the annotation explains why and links to the exact line that shows the connection, usually in another file. Links go to the code, not to the review comments, and are verified before posting.

### 5. Screenshots for UI components

The relevant annotation includes a screenshot from the running UI with a red outline around the component. If the UI cannot be captured or the image cannot be attached, the agent reports what is missing.

## When it stays quiet

File coverage is unconditional. The judgment call applies one level down - **to methods and individual hunks, where most code does not need its own comment.** A helper that title-cases each word in a string, or a `DEBOUNCE_MS = 300` constant, is already clear to anyone qualified to review it; its file comment has already set the context, so an inline note there spends the reviewer's attention and returns nothing. But a six-line helper inside a custom encoding scheme does need explaining, even though it is shorter.

The test is not the size of the code, it is the **inferential distance**: would a competent reviewer be left with a question that one sentence from the author would answer?

```js
// no comment - the name and body say everything
function titleCase(s) { /* ... */ }

// annotated - 6 lines, but you cannot tell whether it is correct
// without knowing which encoding contract it implements
function packHeader(flags, len) {
  return ((flags & 0x0f) << 12) | (len & 0x0fff);
}
```

Inline annotations are also skipped for renames, formatting, mechanical test updates, and idiomatic boilerplate - those files still get their one-line file comment, which is what lets you skip them *knowingly*. Autogenerated output gets nothing at all. The full rule set, with borderline cases, is in [`skills/annotate-merge-request/references/significance-test.md`](skills/annotate-merge-request/references/significance-test.md).

## The main trade-off: comment noise

**The honest downside of this approach is that a merge request fills up with comments, and past some density that distracts more than it helps.** A diff buried in forty explanations is worse to review than a bare one - the reviewer starts skimming, and skims past the one comment that mattered. With file coverage mandatory, comment volume scales with the number of files you touched: a 30-file MR gets 30 file comments.

Five things keep that readable:

1. **File comments do not interleave with code.** They attach to the file header, so the diff itself stays clean - you meet one explanation as you open each file, rather than finding notes wedged between lines.
2. **One-line discipline.** The file comment always exists, but its length follows what actually changed. A mechanical file described in three paragraphs is treated as a defect, not thoroughness.
3. **Inline comments are budgeted and selective.** At most 3 per file and 12 per MR, and those are **ceilings, not quotas** - nothing tells the agent to use them up, and in a normal MR most files end with zero inline comments on top of their file comment. You can raise the limits; the agent will not raise them on its own.
4. **The overview is capped and never per-file.** At most 7 reading-order entries, at most 5 behavior rows, one line per entry-point *area*, mechanical files collapsed into a single closing line (`+ 14 files of mechanical follow-through`). Per-file detail belongs to the file comments; repeating it in the overview makes both unreadable.
5. **Budget pressure is a signal.** If more than 12 spots in one MR are genuinely non-obvious, the finding is that the MR is too large to review well - and the agent says so instead of posting 30 inline comments.

Two further deliberate choices:

- **Annotations are posted unresolved.** A resolved thread renders collapsed, and expanding every annotation one by one costs more than it saves. The reviewer resolves each as they read it. Where a project requires all threads resolved before merging, that is a real number of clicks with a comment per file - so the agent detects the setting, says so, and offers to bulk-resolve at the end.
- **Annotations are not source-code comments.** They explain *this change* to *this reviewer* - information that belongs in the review, not in the codebase forever.

## Staying true after every push

New commits silently invalidate annotations: the described line moves, its logic changes, the file disappears, or a new non-obvious hunk arrives with nothing explaining it. **A stale annotation is worse than a missing one** - the reviewer trusts it and reviews code that is no longer there.

So the plugin has a second mode, run after every push, which re-checks each existing annotation against the new diff and classifies it:

| | | |
|---|---|---|
| `ok` | anchor and fingerprint unchanged | left completely alone |
| `moved` | same code, new line | re-anchored |
| `stale` | the code it described changed | re-read and rewritten in place |
| `orphaned` | file or hunk is gone | removed |
| `MISSING` | a changed file has no file comment (usually added by this push) | annotated - mandatory coverage |
| `uncovered` | new hunk, no inline comment | annotated if it passes the significance test |

Comments are edited rather than reposted where possible, so reviewer replies survive. A comment a human replied to is never deleted. Code-line links are rechecked even if the annotation's own file did not change, and screenshots are refreshed when the UI they show changes. A resolved annotation that goes stale is reopened, since the reviewer's "I read this" no longer covers the code that is there now.

Each comment carries an invisible marker (`<!-- sdmr:v1 ... -->`) holding its anchor and a fingerprint of the code it describes - per-hunk for inline comments, per-file for file comments. That is what makes the agent's own comments identifiable, and what distinguishes "the line number moved" from "the code changed".

## Platform support

| Platform | Status |
|---|---|
| **GitLab** (MRs, `glab`) | Diff annotations via the Discussions API with a `position` object (`position_type=file` / `text`). |
| **GitHub** (PRs, `gh`) | Diff annotations via review comments (`subject_type=file` / `line`+`side`). |
| **Bitbucket** | **Untested.** A documented mapping is included and may well work, but it has not been run against a live instance - the agent will tell you so before posting. |

The agent detects the platform from the git remote and finds the open MR for the current branch. It defaults to showing you a **dry-run preview** in the conversation and posts only after you approve.

## What it is not

- **Not a code review.** It explains; it does not approve, praise, or critique. If the agent finds a defect while annotating, it tells you in conversation and fixes it - it does not post a comment presenting a bug as intent.
- **Not a call-graph guesser.** Every edge in the entry-point graph is verified by searching the repo. Chains that cannot be resolved - dynamic dispatch, DI containers, string-keyed registries - are marked `entry point unresolved`, because a fabricated caller list is confidently wrong and the reviewer will trust it.

## Included scripts

Both are plain Python 3 with no dependencies, and can be run on their own from anywhere (give them an absolute path - the agent does the same, since it runs from your repository, not from the skill directory):

```bash
# map a diff range into the hunks an inline comment could anchor to
python3 skills/annotate-merge-request/scripts/diff_inventory.py \
    "$(git merge-base HEAD origin/main)..HEAD"

# classify existing annotations against the current diff
python3 skills/annotate-merge-request/scripts/sync_state.py \
    --inventory inventory.json --comments comments.json
```

`sync_state.py` accepts the raw comments JSON from any of the three platforms.
