# Annotation format

Three comment shapes: one **overview** comment per MR, one **file** comment per changed file (always, except autogenerated files), and a small number of **inline** comments on non-obvious spots. All three are built from the same sections, at different scales.

Rules that apply to both:

- **Plain language.** Write for a competent engineer who has never seen this code. No jargon the codebase does not already use, no restating the diff in prose ("this adds a function named `x`" is worthless - the reviewer can see that).
- **Say the thing, not that there is a thing.** "Retries are now capped at 3" beats "retry behavior was adjusted".
- **Omit a section rather than padding it.** A section with nothing real to say costs the reviewer a read and teaches them to skim the next one.
- **No review verdicts.** This skill explains; it does not approve, praise, or critique. "This is a clean approach" is noise.
- **Every comment ends with its marker line** (see SKILL.md §7).

## Overview comment

Posted as an MR-level comment (not inline). This is the reviewer's entry point.

```markdown
## What this MR does

<2-3 sentences of intent, in plain language: the problem and the chosen approach.
Why this approach, if an obvious alternative was rejected.>

## Behavior: before → after

| | Before | After |
|---|---|---|
| <observable aspect> | <what happened> | <what happens now> |
| <observable aspect> | <what happened> | <what happens now> |

<Any behavior that is NOT changing but looks like it should be - this is where
reviewers most often misread a diff.>

## Entry points

How the changed code is reached, per area (max 3 levels deep):

- `POST /api/orders` → `OrderController.create` → **`PricingService.quote`** (changed)
- `cli: sync --full` → `SyncRunner.run` → **`PricingService.quote`** (changed)
- `src/utils/retry.ts` → entry point unresolved (registered through the DI container by string key)

## Reading order

1. `src/pricing/service.ts` - the actual change, start here
2. `src/pricing/types.ts` - types the above needs
3. `src/**/__tests__/*` - mechanical follow-through, skim

## Inline notes

- [`service.ts` - rounding order](<url>)
- [`retry.ts` - why the backoff is not exponential](<url>)

<!-- sdmr:v1 kind=overview -->
```

Section notes:

- **Behavior table** - use it when there are two or more observable changes; a single change is clearer as one sentence. For a brand-new component, write "new - no prior behavior" rather than inventing a before-state.
- **Entry points** - one line per changed area, not per function. Bold the changed node. Mark unresolved chains explicitly; never guess (SKILL.md §4).
- **Reading order** - the highest-value section for a large MR and the easiest to get wrong: it must reflect dependency, not file order.

### The overview has a budget too

**Do not enumerate every changed file.** A 60-file MR with a 60-line reading order just moves the wall of text from the diff into the overview comment, and the reviewer skims it the same way.

- **Reading order: at most 7 entries.** List the files that need reading in order; collapse the rest into one closing line - `+ 14 files of mechanical follow-through (test updates, import fixes, lockfile)`. Name the group, not its members.
- **Entry points: one line per changed *area*, not per file.** Files reached through the same chain share a line. If the MR has more than 5 distinct entry chains, that is worth saying out loud: it means the MR spans unrelated areas.
- **Behavior table: at most 5 rows.** More than that and nobody reads the table; pick the changes an operator or user would actually notice and put the rest in prose.
- **Trivial files get no mention at all.** A lockfile bump, a rename, a formatting pass - these appear only inside the collapsed group line, if anywhere.

If the overview cannot be written inside these limits without losing something a reviewer needs, the honest finding is that the MR is too large to review as one unit. Say that to the user instead of writing a longer comment.
- **Inline notes** - filled in during phase 2 of cross-referencing. If there are no inline comments, drop the section.
- **No per-file detail.** The overview says what the MR does; the file comments say what each file does. Repeating file detail here is the fastest way to make both unreadable.

## File comment

One per changed file, anchored at file level (`subject_type=file` on GitHub, `position_type=file` on GitLab). Mandatory for every file except autogenerated/vendored output. This is the comment the reviewer meets when they open a file, so it answers "what am I looking at and why" before they read a single line.

```markdown
**Role:** <what this file does in the change - one line>

**Why it changed:** <1-3 sentences of intent, specific to this file>

**Before → after:** <what differs in behavior; omit if nothing observable changed>

**Reached from:** <entry-point chain for this file, max 3 levels, or "entry point unresolved (<reason>)">

<!-- sdmr:v1 kind=file slug=pricing-service anchor=src/pricing/service.ts ffp=cf13b644b329 -->
```

### Length follows substance

The file comment always exists; how much it says depends on what changed.

**Full form** - a file with real logic changes:

```markdown
**Role:** Owns invoice total calculation.

**Why it changed:** Tax was applied after rounding, so multi-item invoices drifted by up
to a cent per item (#4412). The order of the two operations is now fixed.

**Before → after:** Totals on multi-item invoices change by at most 1 cent. The stored
rounding mode is untouched, so historical invoices are unaffected.

**Reached from:** `POST /api/orders` → `OrderController.create` → `PricingService.quote`

<!-- sdmr:v1 kind=file slug=pricing-service anchor=src/pricing/service.ts ffp=cf13b644b329 -->
```

**One-line form** - a mechanical change. Write it so the reviewer can skip the file with confidence:

```markdown
Import paths only - follows the rename of `PricingService`; no behavior change.

<!-- sdmr:v1 kind=file slug=order-controller anchor=src/orders/controller.ts ffp=81ab20f4c7de -->
```

**Deleted file** - often the most useful annotation in the MR:

```markdown
Deleted. Its only caller was `SyncRunner`, which now uses `PricingService.quote` directly
(see [[ref:pricing-service]]). No other references remained - verified with `rg 'LegacyQuote'`.

<!-- sdmr:v1 kind=file slug=legacy-quote anchor=src/pricing/legacy-quote.ts ffp=9f2c4411ab08 -->
```

**New file** - say what it is for and who uses it, never "new file added":

```markdown
**Role:** Tenant-aware cache key builder, extracted so pricing and billing derive keys
the same way.

**Reached from:** `PricingService.quote` and `BillingJob.run` (both in this MR -
see [[ref:pricing-service]])

<!-- sdmr:v1 kind=file slug=cache-key anchor=src/cache/key.ts ffp=4c8ab3a4b2c1 -->
```

Since every file gets one of these, **a mechanical file described in three paragraphs is a defect.** Volume now scales with file count: the discipline that keeps an MR readable is one-line comments where one line is the truth.

### Spec and test files use a different shape

For a test or spec file, the standard template answers the wrong questions. Nothing *calls* a spec file, so the entry-point section is empty by construction, and "before → after behavior" is about the system, not about the file. What a reviewer needs from a spec file is: **what does it cover now, and which cases did this MR touch?**

So a spec file's comment is a list of its test cases instead:

```markdown
**Covers:** `PricingService.quote` (see [[ref:pricing-service]])

**Changed cases**

- **applies tax after rounding** - `adapted` (expectation): expected total changed
  12.00 → 12.01, because tax is now applied before rounding. The old number encoded
  the bug from #4412.
- **keeps per-tenant rounding independent** - `added`: covers the new tenant argument;
  two tenants with the same cart must not share a rounded total.
- **rejects a negative tax rate** - `removed`: the validation moved into
  `TaxRate.parse`, which has its own cases in [[ref:tax-rate-spec]].

**Unchanged (2):** returns 0 for an empty cart; is deterministic

<!-- sdmr:v1 kind=file slug=pricing-spec anchor=__tests__/pricing.test.ts ffp=752ed2b6d862 -->
```

Rules that make this readable and honest:

- **Statuses are computed, not guessed.** `python3 "$SKILL/scripts/diff_inventory.py" <range> --json` emits `test_cases` per spec file with each case's `name`, `status` (`unchanged` / `adapted` / `added` / `removed`) and line. Derive the list from that; do not eyeball the diff for it. Case names come qualified by their enclosing `describe`/`context` block (`PricingService > quote > applies tax after rounding`) - keep that qualification when a bare name would be ambiguous.
- **Full coverage by name, detail only where it changed.** Every case the file now contains is accounted for, but only `adapted` / `added` / `removed` cases get a description. Unchanged cases are one line of names - and once there are more than about 10, a count plus the group they belong to (`**Unchanged (34):** all of the currency-formatting cases`).
- **`adapted` must name its category.** Either `(call shape)` - signature, mocks, fixtures, imports changed, expectation intact - or `(expectation)` - the asserted result itself changed. These are not comparable risks: an expectation that moved is where an AI quietly makes a failing test pass by agreeing with the code. Say what it was before and after, as numbers or values when they are short.
- **`removed` must say where the coverage went.** Moved to another file (cross-reference it), subsumed by another case, or genuinely dropped because the behavior no longer exists. "Removed" with no reason is the one annotation a reviewer cannot act on.
- **`added` says what contract it pins**, not that a test was added.
- **Ordering:** `adapted` first, then `added`, then `removed`, then the unchanged line. Highest-risk first, same as the script's output order.

The `**Covers:**` line replaces the entry-point graph: a pointer to the code under test, cross-referenced to that file's own comment when it changed in this MR. If the spec covers something not touched by this MR, name it anyway - it tells the reviewer which contract is being pinned.

One caveat to know about the computed statuses: a case's body is sliced from its own declaration to the next one, so editing shared setup that sits between two cases can mark a neighbouring case `adapted`. The bias is deliberate - toward flagging something for a second look, never toward silence - but if you read the diff and the case is genuinely untouched, move it to the unchanged line and say nothing further.

### Autogenerated files get nothing

No file comment at all for lockfiles, `dist/`, `build/`, `vendor/`, `node_modules/`, minified bundles, snapshots, codegen output. They are the only exemption from mandatory coverage. If the overview's reading order mentions them, it is as part of the collapsed group line (`+ 3 generated files`), never individually.

## Inline comment

Anchored to a specific new-side line inside a hunk. Only for spots that pass the significance test - most files get none, because their file comment already told the story. Shorter than the overview - it is read inside a cramped diff view.

```markdown
**Why:** <1-2 sentences. The question the reviewer would have asked.>

**Before → after:** <one line, or omit if this hunk changes no behavior>

**Reached from:** <entry point chain, or omit if the same as the overview's>

<!-- sdmr:v1 kind=inline slug=rounding-order anchor=src/pricing/service.ts@84 fp=a1b2c3d4 -->
```

Three to six lines total. If an inline comment needs more than that, it is really about the file (move it into the file comment) or about the MR as a whole (move it into the overview and link to the line from there).

### Worked example - annotate

```diff
+  const total = round(subtotal * (1 + taxRate), 2);
-  const total = round(subtotal, 2) * (1 + taxRate);
```

```markdown
**Why:** Tax must be applied before rounding, otherwise each line item rounds twice and
invoices drift by up to a cent per item - the bug in #4412.

**Before → after:** Totals change by at most 1 cent on multi-item invoices; the stored
rounding mode is unchanged, so historical invoices are not affected.

**Reached from:** `POST /api/orders` → `OrderController.create` → `PricingService.quote`

<!-- sdmr:v1 kind=inline slug=rounding-order anchor=src/pricing/service.ts@84 fp=a1b2c3d4 -->
```

### Worked example - skip

```diff
+const DEBOUNCE_MS = 300;
```

No comment. The name states the unit and the purpose; 300ms is an unremarkable value. Annotating it would spend reviewer attention to tell them what they already read.

## Cross-reference tokens

While drafting, write cross-links as `[[ref:<slug>]]`:

```markdown
**Why:** The cache key now includes the tenant id because `TenantResolver` started
returning per-tenant configs in this same MR - see [[ref:tenant-resolver]].
```

Slugs are stable, lowercase, hyphenated, and unique per MR. After posting, replace every token with a real link to the posted comment (SKILL.md §6, phase 2). A `[[ref:...]]` token left in a posted comment is a visible defect - grep the final bodies for `[[ref:` before declaring done.
